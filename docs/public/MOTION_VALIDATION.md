Motion document validation follows [`shellx-motion/motion-validation@1`](../../schemas/motion.schema.json). Its stages always run in this order:

1. **structural** — Portable JSON shape, required fields, primitive bounds, and declared built-in payload forms. Authority: `schemas/motion.schema.json`.
2. **semantic** — Document-wide graph integrity, cross references, ordering, renderer constraints, and execution budgets. Authority: `packages/core/src/validate.ts`.

A passing JSON Schema check is **not** proof that a package is renderable. A passing two-stage validation is also **not** proof of a rendered artifact; run preview or render and inspect its receipt for renderer/output evidence.

The CLI, Debug API/MCP, and local SDK expose the same completed validation report vocabulary: `failed/not_run` for structural failure, `passed/failed` for semantic failure, or `passed/passed` for a two-stage pass; `renderability` remains `not_proven` until a render receipt is inspected.
